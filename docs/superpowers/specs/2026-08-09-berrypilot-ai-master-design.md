# BerryPilot AI 产品与技术总设计

> 文档状态：第一版基线设计  
> 编写日期：2026-08-09  
> 项目目标：将现有 Vue 3 课程电商项目升级为可用于前端实习和全栈 AI Agent 秋招的可演示、可测试、可部署项目。

## 1. 产品定位

BerryPilot AI 是一个拥有完整商品、SKU、库存、购物车和订单链路的 AI 原生电商平台。“Berry”代表鲜活、精选和草莓主题，“Pilot”代表能够协助用户规划并执行购物任务的智能副驾驶。用户既可以通过传统商城界面完成购物，也可以通过自然语言向 AI 购物决策与交易 Agent 描述预算、用途、偏好和限制条件，由 Agent 检索商品知识、比较方案并调用真实业务工具。在任何会改变用户数据或交易状态的操作执行前，系统都必须请求用户确认。

该项目不以“给商城增加聊天框”为目标，而以“构建可执行、可控制、可评测的购物 Agent”为核心差异点。

### 1.1 品牌表达

- 英文名称：`BerryPilot AI`；
- 中文描述：草莓智能选购与交易平台；
- 产品短句：`Pick better. Shop with clarity.`；
- 中文短句：把偏好说出来，把选择交给证据；
- Agent 名称：`Berry`，界面中称“购物副驾驶”，避免使用“客服机器人”；
- 品牌性格：清新但不幼稚、友好但不拟人过度、可信且重视解释。

品牌文案必须描述用户能完成的动作，不堆叠“颠覆、智能、未来”等空泛词汇。Agent 推荐必须同时展示依据、限制和不确定性。

## 2. 求职目标

项目需要支持两套真实且不冲突的简历叙事。

### 2.1 前端实习叙事

- Vue 3 与 TypeScript 工程能力；
- 复杂组件、SKU、购物车和订单状态建模能力；
- SSE 流式交互和 Agent 执行过程可视化能力；
- 性能优化、异常恢复、自动化测试和 CI 能力；
- 对用户体验、可访问性和响应式布局的理解。

### 2.2 全栈 AI Agent 秋招叙事

- 从前端、API、数据库到部署的端到端交付能力；
- 商品、库存、购物车和订单系统的业务建模能力；
- RAG、Tool Calling、工作流编排和 Human-in-the-loop 能力；
- 幂等、事务、权限、审计和失败恢复等可靠性设计；
- Agent 评测、Tracing、Token 成本和延迟监控能力。

同一代码仓库承载两种叙事，不维护两个功能分叉的项目。

## 3. 核心用户任务

用户输入：

> 预算 500 元，帮我选择一套适合宿舍使用的咖啡设备，不要胶囊机，尽量静音。

系统执行：

1. 提取预算、场景、排除条件和偏好；
2. 搜索候选商品；
3. 查询商品详情、SKU、库存、评价摘要和知识库资料；
4. 按硬约束过滤，按偏好排序；
5. 生成多个可解释方案并展示依据；
6. 用户选择方案；
7. 系统展示待执行购物车变更；
8. 用户明确确认；
9. Agent 调用业务工具并返回结果。

## 4. 产品范围

### 4.1 传统电商功能

- 用户注册、登录、退出和登录状态恢复；
- 商品分类、搜索、筛选和排序；
- 商品详情、图片预览和 SKU 组合选择；
- 游客购物车、登录购物车和登录合并；
- 收货地址管理；
- 订单预览、创建、查询和状态展示；
- 模拟支付结果，不接入真实资金交易；
- 响应式布局、空状态、加载状态和错误状态。

### 4.2 AI 购物 Agent 功能

- 自然语言需求理解和多轮澄清；
- 预算、用途、偏好和排除条件提取；
- 商品检索、知识问答和多商品参数对比；
- 单品与组合方案推荐；
- 商品库存和价格检查；
- 购物车查询和变更；
- 订单金额预估和订单草稿生成；
- 写操作确认；
- 工具执行结果解释；
- 会话历史恢复；
- 执行中止、超时重试和失败降级。

### 4.3 第一版明确不做

- 自训练或微调大模型；
- 多 Agent 自由协商；
- 无人确认的自动下单；
- 真实支付资金链路；
- 复杂物流和售后系统；
- 商家入驻和多租户结算；
- Kubernetes 集群；
- 以算法研究为目标的个性化推荐系统。

## 5. Agent 工具与安全

### 5.1 只读工具

- `search_products(query, filters, page)`：检索商品；
- `get_product_detail(productId)`：获取商品、规格和详情；
- `compare_products(productIds)`：生成规范化商品对比数据；
- `check_inventory(skuIds)`：查询 SKU 库存；
- `get_product_evidence(productId, question)`：检索商品知识证据；
- `get_cart()`：获取当前用户购物车；
- `calculate_order(items, addressId)`：计算商品、运费和应付金额。

### 5.2 写工具

- `add_to_cart(skuId, count, idempotencyKey)`；
- `remove_from_cart(skuId, idempotencyKey)`；
- `update_cart_item(skuId, count, selected, idempotencyKey)`；
- `create_order_draft(items, addressId, idempotencyKey)`。

### 5.3 安全规则

- 只读工具可自动调用；
- 写工具必须获得当前会话中的明确用户确认；
- 确认内容必须展示商品、数量、价格影响和目标操作；
- 确认后若关键参数变化，原确认立即失效；
- 每个写操作必须携带幂等键；
- Agent 服务不得直连业务数据库，只能调用受鉴权的业务 API；
- 每次工具调用记录用户、会话、参数摘要、结果、耗时和错误；
- 模型输出不能绕过服务端参数、库存和权限校验。

## 7. 前端设计

保留并重构现有首页、分类、详情、购物车、结算和支付页面。核心业务组件通过明确的 TypeScript 接口接收数据，不依赖页面内部私有结构。

Agent 工作台拆分为：

- 会话列表；
- 消息列表和用户输入区；
- 流式回复渲染器；
- 工具调用状态卡片；
- 商品推荐卡片和商品对比表；
- 待确认操作卡片；
- 执行结果卡片；
- 中止、重试和恢复控件。

前端只展示服务端提供的安全状态摘要，不展示模型私有推理过程。

状态边界：

- 用户状态负责身份、Token 生命周期和权限；
- 购物车状态负责本地购物车、服务端购物车和同步队列；
- 商品查询优先使用请求缓存，不把全部服务端数据存入 Pinia；
- Agent 状态负责会话、流式事件、待确认操作和恢复位置；
- 对话框和主题等局部 UI 状态尽量保留在组件内。

### 7.1 视觉主题：草莓实验室

视觉方向不是卡通水果商城，而是“新鲜食材标签 + 精密选择工具”的结合：草莓提供识别度，实验室式信息结构传达可靠、可比较和有证据。页面保留充足留白，草莓元素集中用于品牌入口、关键动作和 Agent 状态，不把每张卡片都装饰成水果。

颜色令牌：

- `Berry Red #E9435E`：主操作、选中态和品牌焦点；
- `Ripe Red #C92F4A`：按压态和高对比强调；
- `Leaf Green #34745A`：成功、库存和可持续提示；
- `Cream #FFF8F3`：主背景，避免纯白带来的模板感；
- `Blush #FBE2E6`：轻提示、筛选标签和 Agent 过程背景；
- `Cocoa #35282C`：主要文字；
- `Stone #766B6E`：辅助文字和边界信息。

所有组合必须满足 WCAG AA 对比度。错误状态使用独立语义色，不用品牌红同时表达“品牌”和“错误”。

字体和排版：

- 中文正文优先使用 `MiSans`，系统不可用时回退到现代无衬线字体；
- 英文展示文字使用有圆润切口但不过度可爱的字体，最终选择必须允许 Web 使用和开源分发；
- 金额、库存、延迟和 Token 等数据使用等宽数字特性；
- 标题层级依靠字号、字重和间距，不依靠大量渐变与阴影。

布局原则：

- 首页首屏以“说出需求”作为核心交互，不使用传统大幅轮播图主导页面；
- 商品区采用编辑式货架布局，突出使用场景、证据标签和可比较参数；
- Agent 页面采用“对话 + 任务轨迹 + 商品证据”三层信息结构；
- 购物车和订单页优先表达价格变化、库存状态和下一步动作；
- 桌面端保持高信息密度，移动端将轨迹和证据折叠为可展开面板。

### 7.2 标志性视觉与动效

项目的唯一高识别度元素是 `Berry Trail`：由草莓籽形状抽象出的任务节点轨迹，用于展示 Agent 从理解需求、检索、比较、等待确认到执行完成的状态。它既是品牌元素，也是有真实信息含义的流程组件。

动效约束：

- 流式回复只对新增内容做轻量显现，不逐字弹跳；
- 工具状态变化使用一次短促的节点过渡；
- 商品卡片不使用无意义漂浮或大面积视差；
- 支持 `prefers-reduced-motion`，减少动效时不影响状态理解；
- 页面只保留一个主要编排动效，其余交互以即时反馈为主。

### 7.3 图片与素材策略

现有小兔鲜 Logo、Banner、二维码、登录背景和品牌相关商品示意图不得进入最终公开版本。阶段一建立资产清单并逐项替换，不允许简单改色后继续使用。

新素材分为：

- 品牌资产：BerryPilot 标志、Favicon、草莓籽轨迹和空状态插画；
- 场景资产：厨房、宿舍、通勤、户外等真实选购场景图；
- 商品资产：授权明确的商品图、自产占位图或 AI 生成的虚构商品图；
- Agent 资产：工具状态、证据引用和确认操作所需的图形语言。

素材要求：

- 自制或 AI 生成素材必须保持统一光线、背景和裁切比例；
- 不仿制现有电商品牌 Logo、角色或受保护视觉资产；
- 每张内容图片提供有意义的 `alt` 文本，纯装饰图使用空 `alt`；
- 优先输出 AVIF/WebP，并保留尺寸信息避免布局抖动；
- 建立素材来源与许可证记录；
- 页面开发时先使用明确标记的原创占位资产，不能为了赶进度重新引用小兔鲜素材。

### 7.4 组件语言

- 卡片圆角保持克制，商品卡片与任务卡片使用不同层级而非统一“大圆角”；
- 按钮文案使用“加入购物车”“确认加入”“重新检索”等明确动作；
- 标签区分约束、证据、库存和优惠，不能只靠颜色区分；
- 空状态必须告诉用户下一步可执行动作；
- 错误信息说明发生了什么、哪些数据已保留、如何恢复；
- Element Plus 只作为交互基础，不保留默认主题外观，最终通过设计令牌形成统一组件系统。

## 8. 业务后端设计

核心领域包括 User、Product、Category、SKU、Inventory、Cart、CartItem、Address、Order、OrderItem、AgentConversation、AgentMessage、ToolExecution 和 OperationConfirmation。

可靠性要求：

- 订单创建使用数据库事务；
- 库存检查与扣减必须防止超卖；
- 写接口支持幂等键；
- 购物车合并规则确定且可测试；
- Access Token 过期后通过 Refresh Token 刷新；
- 业务异常使用稳定错误码；
- Agent 工具与 REST 接口复用同一领域服务，避免两套业务规则。

## 9. RAG 与 Agent 工作流

商品知识来源包括商品标题、结构化参数、详情、SKU、使用说明、模拟评价、常见问题和平台规则。

检索流程：

1. 数据清洗和字段标准化；
2. 按商品和语义段落切分；
3. 生成 Embedding 并写入向量存储；
4. 使用关键词与向量混合检索；
5. 按结构化约束过滤；
6. 对候选证据重排；
7. 将证据和结构化商品数据提供给模型；
8. 返回可追溯的商品来源。

Agent 状态包括：

- `UNDERSTAND`：提取目标和约束；
- `CLARIFY`：信息不足时提问；
- `PLAN`：确定检索和工具步骤；
- `EXECUTE_READ`：调用只读工具；
- `SYNTHESIZE`：生成候选方案；
- `WAIT_CONFIRMATION`：等待写操作确认；
- `EXECUTE_WRITE`：调用写工具；
- `COMPLETE`、`FAILED` 和 `CANCELLED`。

工作流必须设置最大步骤数、总超时和单工具超时。

## 10. 错误处理与降级

- 模型不可用：展示可重试错误，不执行写操作；
- 向量检索不可用：降级为结构化商品搜索；
- SSE 断线：使用事件序号恢复，不重复执行写工具；
- 工具超时：记录失败并进行有限重试；
- 库存变化：废弃旧确认并要求重新确认；
- Token 过期：刷新成功后恢复请求，失败则保留页面并引导登录；
- Agent 输出校验失败：拒绝调用工具并重新生成结构化输出；
- 订单结果不确定：通过幂等键查询最终状态，不盲目重复创建。

## 11. 测试、评测与可观测性

### 11.1 前端测试

- SKU 路径选择和禁用状态；
- 购物车金额与选择状态；
- SSE 事件归并和断线恢复；
- 写操作确认组件；
- 登录、加购、结算和 Agent 加购 E2E。

### 11.2 后端测试

- 鉴权与权限；
- 购物车合并；
- 幂等写操作；
- 库存并发；
- 订单事务；
- Agent 工具契约。

### 11.3 Agent 评测

- 约束提取正确率；
- 商品检索召回质量；
- 推荐硬约束满足率；
- 引用是否支持回答；
- 工具选择和参数正确率；
- 写操作确认绕过率必须为零；
- 任务完成率；
- 平均响应延迟和单任务 Token 消耗。

一次 Agent 任务至少记录请求、用户和会话 ID，工作流状态，模型和 Prompt 版本，工具耗时与结果，引用文档，Token，用时和降级原因。日志不得记录密码、完整 Token 和不必要的隐私数据。

简历只使用可由脚本或报告复现的真实数据。

## 12. 四阶段路线

### 阶段一：前端基线与 AI 交互原型

目标：得到可投递纯前端实习的稳定版本，并建立后续扩展边界。

范围：

- 修复登录、购物车、路由和支付回调等关键问题；
- 清理课程项目和调试痕迹；
- 将项目品牌、界面文案和元数据统一迁移为 BerryPilot AI；
- 建立颜色、排版、间距、圆角、阴影和动效设计令牌；
- 盘点并替换小兔鲜 Logo、Banner、背景图和其他品牌素材；
- 重构首页信息架构，减少传统课程商城的轮播图和商品楼层痕迹；
- 建立 TypeScript 迁移策略并迁移核心业务；
- 重构请求、鉴权、购物车和错误处理；
- 路由懒加载；
- 增加 Vitest、Vue Test Utils 和 Playwright；
- 实现基于 Mock Agent 服务的 SSE 流式交互原型；
- 增加响应式、键盘操作和 reduced-motion 基础支持；
- 增加性能基线、素材来源记录、README、截图和演示说明。

验收：生产构建、Lint 和测试通过；登录、SKU、游客加购、登录合并和结算链路可演示；Agent 原型支持流式消息、Berry Trail 工具步骤和写操作确认；公开页面不再出现小兔鲜品牌资产和课程测试文案；核心页面在桌面与移动视口可用；品牌颜色达到 WCAG AA；形成包含真实截图和性能基线的前端简历草稿。

### 阶段二：自建全栈业务后端

目标：替换教学 API，形成独立电商系统。

范围：NestJS、Prisma、PostgreSQL、Redis、用户、商品、SKU、库存、购物车、地址、订单、JWT、幂等、事务、库存并发保护、OpenAPI、Docker Compose，以及前端 API 迁移。

验收：核心购物链路不依赖教学 API；数据库可通过种子数据重建；关键测试通过；服务可用文档化命令启动。

### 阶段三：真实 Agent、RAG 与工具调用

目标：完成可执行、可控制、可评测的购物 Agent。

范围：FastAPI、LangGraph、模型适配层、商品知识库、混合检索、读写工具、Human-in-the-loop、会话持久化、SSE 协议、超时重试、降级、Trace 和评测集。

验收：Agent 完成至少三类代表性购物任务；写操作无法绕过确认；工具和 RAG 有自动评测；能够查看完整执行链路、延迟和 Token；形成全栈 Agent 简历草稿和演示脚本。

### 阶段四：求职增强与公开交付

目标：把可运行项目转化为可信求职材料。

范围：性能与可靠性优化、CI/CD、在线部署、安全检查、架构图、演示视频、项目主页、两版简历、面试讲稿；时间允许时增加 MCP Server 或评测后台。

验收：演示环境可访问；README 能让陌生开发者独立启动；所有简历数字可复现；项目可按 3 分钟、10 分钟和 30 分钟讲解。

## 13. 跨对话交接协议

每个阶段使用独立对话。仓库文档、测试结果和 Git 状态是事实来源，聊天记忆不是事实来源。

### 13.1 新对话开始时必须阅读

1. 本总设计；
2. 当前阶段实施计划；
3. 最新交接文档；
4. `git status` 和最近提交；
5. 当前任务相关源码和测试。

### 13.2 每个阶段必须产出

- 阶段设计或实施计划；
- 阶段交接文档；
- 测试与验证结果；
- 新环境变量、数据库和 API 变化；
- 尚未完成和已知问题；
- 下一阶段推荐起点。

### 13.3 交接文档固定结构

```markdown
# 阶段 N 交接

## 本阶段目标
## 已完成内容
## 关键设计决策及原因
## 创建和修改的文件
## 数据库/API/事件协议变化
## 验证命令与结果
## 性能或评测数据
## 当前 Git 状态
## 未完成内容与已知问题
## 下一阶段第一步
## 新对话启动提示词
```

### 13.4 提交规则

- 不覆盖用户已有的未提交修改；
- 每个可独立验证的任务形成聚焦提交；
- 交接前运行与风险相称的验证；
- 未通过验证的内容不得写成“已完成”；
- 密钥不进入 Git；
- 计划变化必须写回文档。

## 15. 已确认决策

- 最终目标采用完整可投递版，分阶段交付；
- 前端保留 Vue 3 并迁移 TypeScript；
- 业务后端使用 NestJS，Agent 服务使用 FastAPI；
- 第一版采用单 Agent，不采用多 Agent；
- 所有交易写操作采用 Human-in-the-loop；
- Agent 通过业务 API 调用领域能力，不直连业务数据库；
- 第一阶段使用 Mock Agent 协议，真实 Agent 在第三阶段实现；
- 品牌名称采用 BerryPilot AI，视觉方向采用克制的草莓实验室主题；
- 最终公开版本不复用小兔鲜品牌图片和课程项目文案；
- Agent 任务轨迹使用 Berry Trail 作为核心识别组件；
- 每个阶段使用独立对话，通过仓库交接文档衔接。

## 16. 成功定义

- 用户能通过传统界面和 Agent 两种方式完成可靠购物流程；
- Agent 能调用真实工具且不能绕过安全确认；
- 前端、业务后端和 Agent 服务边界清晰并可独立测试；
- 项目拥有可复现的性能、测试和 Agent 评测数据；
- 陌生开发者能够根据文档启动和理解系统；
- 同一项目能够形成可信的前端实习和全栈 AI Agent 两套简历叙事。
